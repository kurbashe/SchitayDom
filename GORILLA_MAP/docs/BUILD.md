# Сборка двух пакетов GORILLA MAP

Нужен Python 3.10+. Сторонние Python-пакеты для упаковки не требуются. Команды выполняются из корня проекта:

```sh
python tools/test_packaging.py
python tools/test_source_checks.py
python tools/verify.py
python tools/build.py
python tools/verify.py --pbo dist/@GorillaMap/addons/gorillamap.pbo --server-pbo dist/@GorillaMapServer/addons/gorillamap_server.pbo
```

Результат:

- `dist/@GorillaMap/addons/gorillamap.pbo` — клиентский интерфейс и общий протокол. Префикс `GorillaMap`. Метаданные берутся из корневого `mod.cpp`.
- `dist/@GorillaMapServer/addons/gorillamap_server.pbo` — серверная логика и хранилище. Префикс `GorillaMapServer`. Метаданные берутся из корневого `mod_server.cpp`.
- `dist/GORILLA_MAP.zip` — оба пакета, оба набора исходников, документация, инструменты и образец серверного профиля.
- `dist/build-manifest.json` — SHA-256 обоих PBO и каждого исходного файла, статус неподписанной сборки.

Для другого выходного каталога используйте `python tools/build.py --output /путь/к/сборке`. Инструмент создаёт выходные папки и архив; существующие сохранения сервера не читает и не меняет.

## Разделение поставки

| Где | Параметры |
|---|---|
| Клиент | `"-mod=@GorillaMap"` |
| Сервер | `"-mod=@GorillaMap" "-serverMod=@GorillaMapServer"` |

Клиентам передаётся **только `@GorillaMap`**. Администратор вручную устанавливает **оба пакета** на сервер. Серверный пакет не генерируется при запуске и не рассылается игрокам. При запуске создаются JSON-файлы профиля, а не PBO.

`GorillaMapServer/config.cpp` явно зависит от `CfgPatches.GorillaMap`. Общие типы DTO находятся в `3_Game` клиентского/общего пакета и доступны серверному пакету. Клиентский пакет не ссылается на `GorillaMapServer`, `GMapService` и классы серверного хранилища. Проверки сборки отклоняют утечку этих типов в клиентский PBO и GUI-ресурсов в серверный PBO.

## Что подтверждает упаковщик

Сборка воспроизводима: файлы упорядочены, даты записей фиксированы. Оба PBO содержат штатный SHA-1 trailer. Схема заголовков сверена с открытой реализацией [armake](https://github.com/KoffeinFlummi/armake/blob/master/src/build.c); код armake в проект не включён.

`build.py` упаковывает скрипты и текстовые `config.cpp`. Он не компилирует Enforce Script, не биниризует ресурсы и не создаёт цифровую подпись. `verify.py` проверяет структуру текста, XML, ссылки на ресурсы и виджеты, регистрацию модулей и зависимость серверного пакета от общего. Параметры `--pbo` и `--server-pbo` дополнительно проверяют точное соответствие упаковки исходникам. Эти проверки не подтверждают работу в движке.

## Сборка штатными инструментами Windows

Альтернатива: DayZ Tools → Addon Builder, отдельно для каждого пакета:

| Source | Destination | Prefix |
|---|---|---|
| `Source/GorillaMap` | `@GorillaMap/addons` | `GorillaMap` |
| `Source/GorillaMapServer` | `@GorillaMapServer/addons` | `GorillaMapServer` |

Сохраняйте `.c`, `.layout`, `.xml`, `.paa` в наборе файлов упаковки. Скрипты проверяются при запуске DayZDiag/DayZ, а не самим фактом создания PBO.

## Подпись для сервера

Используйте DSUtils из DayZ Tools и собственную пару ключей. Закрытый `.biprivatekey` хранится вне распространяемого архива. Для клиентского/общего PBO создайте `.bisign` и распространяйте её рядом с PBO. Публичный `.bikey` установите в корневой серверный каталог `keys/`.

Пример PowerShell, где пути заменяются вашими:

```powershell
& 'C:\DayZ Tools\DSUtils\DSSignFile.exe' 'D:\PrivateKeys\GORILLA.biprivatekey' '.\dist\@GorillaMap\addons\gorillamap.pbo'
```

Серверный PBO через `-serverMod` клиентам не отправляется. Его можно подписать тем же инструментом для собственной проверки целостности; это не основание подключать его в клиентском `-mod`.

После любого изменения PBO подпись создаётся заново. В архиве нет фиктивной подписи или чужого ключа. Для публичного сервера с `verifySignatures=2` клиентский/общий PBO должен иметь действующую подпись; изменение этой настройки не является шагом установки.

## Проверка в DayZ

Сначала проверьте чистый dedicated ChernarusPlus без других модов, затем ваш набор модов. Игрок загружает только общий/клиентский PBO; на dedicated загружаются оба. Это проверяет, что клиент компилируется без серверных классов и сервер получает общие DTO через явную зависимость.

Для итогового теста используйте собранные PBO без `-filePatching`, проверьте клиентский и серверный RPT/script logs, личные метки после рестарта, групповые права, приглашения, закрытие UI, масштабирование и координаты карты. Инструменты в этом репозитории не заменяют эти испытания.
